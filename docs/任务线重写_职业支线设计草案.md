## 一、背景与定位

整合包 274 个 mod、武器护甲 2000+ 件（D&C 211、史诗骑士 228、SLU 173、简易刀剑 120、Spore 19…），玩家实际利用率极低。本次重写新增**职业支线**，目标：

1. 提高存量装备/系统的利用率；
2. 让支线承担「整合介绍」职能——任务线本身就是内容导览员；
3. 任务写作风格改为「**像老师一样布置作业**」（见第四节写作规范）。

## 二、三条职业支线（用户原案）

> ⚠️ 用户说"4 个支线"但只列了 3 个，第四条待补。

| 支线 | 内容载体 | 检测对象 | 奖励方向（用户原案） |
|---|---|---|---|
| **收藏家** | 全包武器护甲（也是一种"职业"身份） | 玩家获得武器护甲的**数量与等级** | 属性、钱币（真菌币）、技能书、附魔书、饰品 |
| **锻造师** | 匠魂（TiC + CTI 接入） | 玩家获得匠魂武器护甲的数量与等级 | 匠魂材料、饰品等 |
| **狩龙人** | 圣龙传说 | 玩家**击杀 + 驯服**龙的数量与等级 | 属性、饰品等 |

现成数据资产：`docs/全量武器表.md`、`docs/数值表_武器.md`（收藏家图鉴可直接机器生成）；`docs/CTI匠魂体系分析.md`（锻造师）；敌对生物表与群系标签（狩龙人）。

## 三、技术可行性结论（探讨中已确认的关键约束）

### 1. 「数量与等级」检测是最大的坑，FTB 原生撑不起

- **收藏家**：FTB 物品任务无法做"拥有 N 件不同武器"的计数+去重。可行路径：
  - 用 KubeJS 给装备打**分级物品标签**（`#svs:collect_t1`~`t5`，数据从全量武器表生成），FTB 物品任务按 tag 匹配 → 覆盖"等级"维度；
  - 图鉴式"集齐 N 件"需 KubeJS 自定义任务扫背包统计注册名去重 → 要写脚本，可行。
- **锻造师**：**匠魂工具是单注册名 + NBT 变种**（EF 适配文档中为此前车之鉴），FTB 物品任务 NBT 匹配很脆。更稳的检测对象：
  - 中间产物（部件、材料锭）；
  - 冶炼炉里程碑（建成冶炼炉/首次浇铸等，进度或方块检测兜底）；
  - "武器等级"用"持有含某材料的部件"近似。
- **狩龙人**：最简单。击杀任务原生支持（按实体 ID 计数）；**驯服**检测取决于圣龙传说是否有现成 advancement 可挂（FTB advancement 任务），没有则 KubeJS 事件桥接。

**建议**：「等级」维度一律简化为**标签分档**，不做逐件数值识别。

### 2. 奖励设计的两个冲突点（待裁决）

- **属性奖励无现成通道**：只能靠 FTB 命令奖励调 `/attribute` 或 svs_tweak 加效果。需防与难度体系、共生体加成叠乘失控 → 建议小额、封顶、任务描述里写明规则。
- **EF 技能书归属冲突**：技能书目前是 DailyBoss 日课的招牌奖励（决议二·竞技场日课）。收藏家也发会稀释日课 → 建议收藏家改发附魔书/饰品/真菌币，技能书留日课；或反过来，用户拍板。

### 3. 必须挂阶段门控

支线章节按主线四阶段（《魔改设计决议.md》四：启程→磨砺→天灾防线→反推）逐段解锁。收藏家 T4/T5 图鉴若阶段Ⅰ 就开放，等于鼓励跨阶段刷装，与门控体系冲突。

## 四、「老师布置作业」写作规范（重写通用）

每个任务固定四段式描述：

```
【教学目标】为什么做这件事（一句话，讲机制不讲背景故事）
【作业】    做什么、做到什么程度（= 检测条件）
【提示】    前置清单 + 在哪找 + 预估耗时（沿用探索章"只给方位不给坐标"风格）
【讲评】    完成后一句话反馈：学到的东西接下来在哪用
```

已作废旧框架中可继承的教学基因：序章 EF 键位教学、共生体 Stress 压力管理教学、CDU 部署教学——重写时把隐性教学显性化。

## 五、实施纪律提醒

- FTB 任务 SNBT **只由游戏内任务编辑器生成**（`config/ftbquests/`），严禁手写 SNBT；
- 物品/实体 ID 未核实前一律标【待核实】，落地前 `/ct hand` 或 F3+H 现场确认；
- 奖励原则沿用：材料 > 成品（《整合包开发方案 v4》3.6）；
- 多人按 FTB Teams 队伍共享进度结算。
