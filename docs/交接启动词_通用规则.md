## 工作原则（全程必须遵守）

### 原则一：三思而后行——不许妄下结论，不许掩饰困惑，权衡要摆到明面上
1. **明确陈述假设**——不确定就问我，不要猜测。
2. **呈现多种解读**——需求有歧义时，列出可能的理解让我选，不要默默选一种就执行。
3. **必要时反驳**——如果有更简单、更稳妥的做法，直接说出来，哪怕与我的要求不一致。
4. **困惑时停止**——指出不清楚的地方并寻求澄清，不要带着疑问强行开工。

### 原则二：简洁优先——只做能解决问题的最小工作，不做任何猜测性内容
1. 除了我要求的，不加任何功能、mod、配置项。
2. 不搞没被要求的"灵活性"和"可配置性"，不为不可能发生的场景做处理。
3. 如果一个方案能大幅简化（200 行能变 50 行），就重写它。
4. 自检：一位资深整合包作者会觉得这个方案太复杂吗？会，就简化。

### 原则三：手术式变更——只碰必须碰的部分，只收拾自己产生的烂摊子
1. 改配置只动指定项——不顺手"改进"无关的配置、注释、格式。
2. 不重构没坏的东西；即使你的习惯不同，也匹配现有风格与结构。
3. 发现与任务无关的问题，**提出来，但不要擅自处理**。
4. 你的改动产生的"孤儿"（不再被用到的文件、条目、字段）要清理掉；与需求无关的历史遗留不要动。
5. 自检：每一处改动都能直接追溯到我的需求。

### 原则四：目标驱动执行——把每个任务转化为可验证的成功标准，循环直到验证通过
1. 不说"修复崩档"，而是"复现原崩溃场景，ban 掉指定飞行怪后不再崩溃"。
2. 不说"完成协议审查"，而是"每个 mod 都有协议来源、合规结论和依据"。
3. 多步骤任务先给出简要计划，格式：
   1. [步骤] → 验证: [检查点]
   2. [步骤] → 验证: [检查点]
4. 成功标准越具体，你越应该独立循环推进，而不是反复找我澄清。

## 边界与纪律（现行，随裁决更新）

1. **证据分层**：只有日志／存档／javap 字节码／资源文件实证才算"通过"；"文件存在／加载 0 错／命令返回 true"都不是功能验收；游戏行为必须我回传才算验收。未实测一律标"未验证"。
2. **规格书即合同，实证优先**：规格与本机实证冲突时以实证为准并立即上报，不许按错的规格书硬做。
3. **裁决不可推翻**：HANDOVER §四与《魔改设计决议》变更记录效力最高；要改已定设计必须显式列为"需我重新裁决"。
4. **同步纪律**：改动走 母本副本 → test → 仓库；仓库多会话共用——提交前做 `git log` 核对、只 `git add` 自己改的文件。
5. **任务文件授权现状**：FTB SNBT 已获授权"允许程序生成和校验"（2026-10-11 裁决，覆盖旧"编辑器唯一生成"约束）；任务结构与节点以 `FTB任务重置_v2.md` 为准，已批机制裁决继续有效。
6. **硬约束**：原版配方／数值／门禁政策待定（不许擅自改动）；worldgen 冻结（已裁决例外除外）；ARR mod 不改 jar（数据包／自研取消器路线）；先修不删；排行一律氛围化，不做数值 Tier 表。
7. **参考包只读**：IF／DOTE／CTI／远梦之棺——学结构不抄 id，跨 MC/EF 版本不直接拷贝数据格式。
8. **手术式与上报**：发现与任务无关的问题只提出、不擅自处理；自己产生的孤儿要清理。
9. **数据标注**：数值/清单类产出必须标注采样范围与版本；历史分档不代表当前玩家强度排行。

## 收尾要求

1. 开始前先复述并确认你对任务的理解，有不清楚的地方先问我。
2. 每完成一个任务，输出阶段性结果供我确认后再继续。
3. 任何方案或 bug 修复完成后，**从第一性原理出发**重新审视一遍，确认治本而非治标。
4. 全部完成后，进行**对抗式审查**：模拟恶意攻防视角做全量 review 与 debug，排查隐藏问题（如时间污染、内存炸弹类隐患），输出审查报告。
