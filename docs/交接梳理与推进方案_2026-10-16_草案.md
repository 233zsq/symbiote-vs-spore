## 四、新推进方案

### P0：资料与交接基线（建议下一工作包）

范围：仅仓库文档与离线资料；不启动或修改游戏实例。

1. 按文件类型登记权威入口、有效日期、证据层级、被替代段落与依赖。优先处理上表冲突，保留原档及来源。
2. 只读复核母本/test 的 JAR 文件、版本与哈希差异；225/226 是 10-15 记录，不能直接当 10-16 新盘点结果。保留用户额外安装项，不自动同步。
3. 审查现有生成器，把日期与扫描范围明确化，先产暂存差异；历史 dump、当前静态资源、未来运行时采样分层。
4. 更新统一源后重建六份工作簿与相关目录视图；旧 Boss 表继续作历史参照。保留冻结标签输入与 1291 输出。
5. 在现有 README、索引、HANDOVER、执行状态中维护入口与状态；更新提示词，不复制一套完整事实。

验收：新增/移除/换版差异逐项有路径与哈希；六表与统一源条目对应、日期准确；历史缺值不补零；不出现“静态资源＝实测适配”；链接可达；任务与包体文件无变更。若当前目录与记录冲突，报告差异而非自动修包。

### P1：剧情、战位与玩家路线评审

以前述资料基线为输入，以 v3 的 V3-A～D 为讨论入口。沉降移支、特色优先、大圣身份等已确定方向不重复求批。22 位主线 Boss 加母巢事件、23 场支线是现有提案，不作为硬指标。

每场候选只登记必要字段：实体/事件、来源版本、模型动作证据、EF可玩性状态、入口与重试线索、最终判胜依据、奖励用途、故事职责、依赖及待定事项。没有运行时证据的字段明确待验。

先离线审重复战斗、原生获取路径和奖励冲突；需游戏看样的部分等明确窗口，不把看样与整包功能测试合并。终局、独立大圣工程合入及模组6/模组7汉化等分别处理，不因剧情需要一并批准。

验收：玩家每阶段知道去哪里、为何去、怎样起战、失败怎样重试、胜后获得什么；未验通的路径作为阻塞，不用剧情文字填补。

### P2：明确恢复后，验证最小玩家流程

仅在用户明确恢复对应任务工作后进行。先检查现有 25 pending 的实际条目与依赖，不依据旧计数盲目整本重生成。

建议第一段覆盖：新角色进入 → 教学与初始奖励 → 村民交易/匠魂起步 → 共生里程碑 → 一场有效胜利 → 奖励到账 → 重登保持。优先复用当前 v2 源与 ID 映射；先核源码/生成器的映射稳定性再替换。

验收分项：静态 ID/引用/无环检查；实际完成与发奖；choice 必须选择领取到账；必要的队伍归属与重登验证。加载 210 节点不能替代以上验收。

### P3：章节与系统分批收口

每批围绕一段可玩的完整路线：入口、准备、战斗、最终胜利、收益、下一目标。按已确认战位推进，不为补足旧数量填任务。

围城失守/回拨/两人共享仍独立登记；多人验收前不提前清理所需诊断。性能参数等 spark 证据；EF怪物适配、世界生成例外与触手辅助战二期保持原边界。

验收：每批单列通过与未通过，不把单人结果扩大为多人，不把历史 test19 绿灯扩大为当前全包。

### P4：发布准备

依据实际交付清单核对许可及资源包/光影分发条件，补齐现版覆盖；历史151件审查不能代替全量通过。核对包体、packwiz/index、配置、脚本及发布说明；在授权测试窗口完成新安装与既有存档回归。构建 JDK17 与游戏 JDK21 分开记录。

验收：版本和文件清单可追溯，安装与启动证据齐全，许可缺口有结论，未通过项如实列明。不在本稿安排具体日期或发布动作。
